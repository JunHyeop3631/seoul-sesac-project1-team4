## 범위와 턴의 관계

한 턴에 웨이브 하나를 방어한다. 턴 시작·준비 단계·전투 시작 조건·턴 종료와 다음 준비 단계 전환은 [턴 흐름 명세](TurnSpec.md)에서 다룬다. 이 문서는 웨이브 구성, 몬스터 등장, 전투 진행, 웨이브 완료 판정과 관련 스크립트의 책임을 다룬다.

공격 대상 유지와 타격은 [아군 명세](AllySpec.md), 이동·체력·처치와 재사용 시 초기화는 [적군 명세](EnemySpec.md)에서 다룬다.

사용자가 확정한 규칙과 현재 코드의 연결 상태를 구분한다. [기획 문서](https://docs.google.com/document/d/1NM-D30vqywVCfJryjdS6B17rJT8bwrZYDl4Uoiu8Ojc/edit)의 제안은 별도 확인 없이 확정 규칙으로 적용하지 않는다.

## 확정 규칙

### 시작과 몬스터 등장

- 준비 단계에서 전투 시작 버튼을 누르면 이번 턴의 전투(웨이브)를 시작한다.
- 첫 몬스터는 즉시 등장한다. 첫 등장 전 카운트다운이나 대기시간은 두지 않는다.
- 한 웨이브에 정해진 수의 몬스터가 시간 간격을 두고 순차 등장한다.
- 몬스터 수는 웨이브별로 다르게 설정할 수 있다.
- 등장 간격은 모든 웨이브에서 같은 값을 사용한다.
- 웨이브별 몬스터 수와 공통 등장 간격의 구체적인 값은 미정이다.

### 전투와 몬스터 이탈

- 아군의 공격은 자동으로 진행된다.
- 몬스터가 경로 끝에 도달하면 기지에 피해를 주고 사라진다.
- 적은 윷판 바깥의 오른쪽 아래에서 출발해 위 → 왼쪽 → 아래 → 오른쪽 순서로 한 바퀴 돈다. 출발점으로 돌아오면 적 오브젝트를 비활성화한다.
- 시작 목숨은 10개이며, 몬스터가 목적지에 도착해 사라질 때마다 목숨이 1개 감소한다. 남은 목숨은 0 미만으로 내려가지 않으며 다음 웨이브에도 유지한다. Heart HUD에 남은 목숨을 숫자로 표시한다.
- 기지에 도달해 사라진 몬스터는 처치한 것이 아니므로 처치 재화를 지급하지 않는다. 재화 획득과 이월 규칙은 [턴 명세의 재화·비용](TurnSpec.md#던지기-재화와-비용)을 따른다.

### 완료 조건

다음 두 조건을 모두 만족하면 웨이브가 완료되어 전투가 종료된다.

1. 이번 웨이브에 예정된 몬스터가 모두 등장했다.
2. 필드에 살아 있는 몬스터가 없다.

처치된 몬스터와 기지에 도달해 사라진 몬스터 모두 필드에서 제거된 것으로 처리한다. 예정된 몬스터가 아직 남았다면, 다음 등장 대기 중 필드가 잠시 비어도 웨이브는 완료되지 않는다.

승리 깃발은 웨이브 완료만으로 표시하지 않는다. 예정된 적을 모두 처치하고 잔여 하트가 남아 있어야 한다. 하트 0에 따른 패배 깃발과 결과 표시 이벤트는 [턴 명세의 전투 결과 깃발](TurnSpec.md#전투-결과-깃발)을 따른다.

웨이브 완료를 턴 관리에 알리면, 이후 전투 종료·턴 종료·다음 턴 시작 및 준비 단계 진입은 [턴 종료와 다음 준비 단계](TurnSpec.md#턴-종료와-다음-준비-단계)를 따른다.

## 클래스별 책임과 현재 연결

| 클래스 | 책임 및 연결 |
| --- | --- |
| [TurnController](../Assets/Scripts/Turn/TurnController.cs) | 현재 턴 번호를 보관하고 `WaveManager.StartWave`에 전달한다. 웨이브 완료 알림을 받아 전투·턴 종료 흐름으로 연결한다. |
| [WaveManager](../Assets/Scripts/Wave/WaveManager.cs) | 웨이브 데이터 목록, 실행할 `Wave`, `EnemyPool`, 공통 등장 간격을 참조한다. 전달받은 번호의 데이터를 골라 실행 요청하고 완료 알림을 전달한다. |
| [Wave](../Assets/Scripts/Wave/Wave.cs) | 몬스터를 순차 소환하고, 공격 대상 탐색과 적 이탈 처리, 웨이브 완료 판정을 담당한다. |
| [WaveData](../Assets/Scripts/Wave/WaveData.cs) | 적 ID와 등장 수량 목록을 보관하는 `ScriptableObject`다. |
| [EnemyPool](../Assets/Scripts/Enemy/EnemyPool.cs) | 적 ID와 프리팹 목록을 보관하며, 종류별 풀에서 적을 요청하고 반환한다. |
| [Ally](../Assets/Scripts/Ally/Ally.cs) | 현재 대상을 유지하고 공격 간격에 맞춰 피해를 준다. |
| [Enemy](../Assets/Scripts/Enemy/Enemy.cs) | 경로 이동과 체력을 관리하고, 처치와 경로 도착을 각각 알린다. |

한 턴에 한 웨이브이므로 현재 진행 번호는 `TurnController`에서 관리한다. `currentTurnNumber`는 0부터 시작하며, `WaveManager`에서 별도의 웨이브 번호를 증가시키지 않는다. 전달받은 번호를 배열 인덱스로 그대로 사용하므로 첫 번째 웨이브는 `waves[0]`이다.

### 시작 요청

`TurnController.StartBattle → WaveManager.StartWave(현재 턴 번호) → Wave.StartWave(웨이브 데이터, 적 풀, 공통 등장 간격)`

`WaveManager`는 참조나 해당 번호의 데이터가 없으면 실행 요청을 진행하지 않는다.

### 완료 알림

`Wave.Completed → WaveManager.HandleWaveCompleted → WaveManager.WaveCompleted → TurnController.EndBattle`

`Wave`와 `WaveManager`는 `TurnController`를 직접 참조하지 않는다. 완료 이벤트로 연결하고, 이벤트 구독은 활성화 시 등록하고 비활성화 시 해제한다.

`Wave.StartWave`에서 `spawningComplete`를 초기화한다. 소환 코루틴이 예정된 소환을 마치면 이 값을 켜고 `TryCompleteWave()`를 호출한다. 적이 처치되거나 경로 끝에 도착해 풀로 반환된 직후에도 같은 검사를 실행한다.

`TryCompleteWave()`는 웨이브 실행 중이고, 소환이 완료됐으며, `spawnedEnemies.Count == 0`일 때 완료로 판정한다. `IsRunning`을 먼저 끈 뒤 `Completed`를 한 번 보낸다. 다음 웨이브 번호 증가와 준비 단계 상태 전환은 [턴 명세의 후속 범위](TurnSpec.md#후속-범위)에서 다룬다.

## 적 오브젝트 풀 구조

### 저장 구조와 접근

`EnemyPool`은 적 ID로 종류별 풀을 찾는 딕셔너리와, 재사용할 객체를 보관하는 `ObjectPool<Enemy>`를 구분한다.

적 ID는 문자열 대신 공통 [EnemyId enum](../Assets/Scripts/Enemy/EnemyId.cs)을 사용한다. `Basic_Enemy_left = 0`, `Enemy2 = 1`로 명시하며 웨이브 구성, 프리팹 등록, 풀 딕셔너리의 키와 요청 함수 인자에 같은 타입을 사용한다. Inspector에서는 enum 항목을 선택한다. 씬과 에셋에는 숫자로 저장하므로 적 종류를 추가할 때 기존 숫자를 변경하거나 다른 종류에 재사용하지 않는다. enum에 정의되어 있어도 프리팹 등록이 없으면 소환할 수 없다.

| 저장 위치 | 보관하는 정보 | 접근 목적 |
| --- | --- | --- |
| `enemyPrefabs` 배열 | 적 ID와 프리팹의 Enemy 컴포넌트 참조 목록 | 요청할 적의 원본 프리팹 확인 |
| `pools` 딕셔너리 | `적 ID → ObjectPool<Enemy>` | ID로 해당 종류의 풀 조회 |
| 각 `ObjectPool<Enemy>` 내부 | 반환되어 대기 중인 적 객체 | `Get()`으로 객체를 꺼내고 `Release()`로 반환 |
| `owners` 딕셔너리 | `생성된 적 객체 → 소속 풀` | 객체를 원래 풀로 반환할 때 소속 확인 |

```text
pools
├─ EnemyId.Basic_Enemy_left → Basic_Enemy_left용 ObjectPool → 반환되어 대기 중인 Basic_Enemy_left 객체들
└─ EnemyId.Enemy2 → Enemy2용 ObjectPool → 반환되어 대기 중인 Enemy2 객체들
```

실제 대기 객체의 보관은 `ObjectPool`의 내부 자료구조에 맡긴다. 내부 구현을 `List`로 가정하거나 외부에서 그 목록을 직접 관리하지 않는다. 딕셔너리는 적 객체 하나하나를 탐색하는 대신, 적 종류에 맞는 풀을 조회하는 데 사용한다.

현재 `pools.TryGetValue`의 조회는 평균 `O(1)`이다. 프리팹을 찾는 `FindPrefab`은 별개로 `enemyPrefabs` 배열을 순회하므로 최악 `O(N)`이며, `N`은 등록된 적 종류 수다. 프리팹 딕셔너리 캐싱이나 기존 풀 우선 조회는 아직 적용하지 않았다.

### 배열·리스트와 딕셔너리의 사용 기준

현재 웨이브 관련 코드에서 설정 목록은 `List<T>`가 아닌 배열(`T[]`)로 선언했다. Inspector에서 목록처럼 편집할 수 있지만 C#의 `List<T>`와는 다르다. 풀의 내부 자료구조도 외부에서 사용하는 `List<T>`로 간주하지 않는다.

| 실제 선언 | 사용 방법 | 선택한 이유 |
| --- | --- | --- |
| `WaveManager.waves : WaveData[]` | 현재 턴 번호로 `waves[index]`에 접근 | 웨이브 순서를 보관하고 번호로 바로 선택하기 위한 설정 목록이다. |
| `WaveData.enemies : EnemyGroup[]` | `foreach`로 그룹을 순회하고 각 그룹의 `count`만큼 요청 | 웨이브에 어떤 적이 몇 마리 나오는지 Inspector에서 편집하고 순서대로 읽기 위한 설정 목록이다. 현재 구현은 등록 순서로 처리한다. |
| `EnemyPool.enemyPrefabs : EnemyPrefabEntry[]` | Inspector에 ID·프리팹을 등록하고 `FindPrefab`에서 순회 | 프리팹 참조를 편집 가능한 설정으로 보관한다. 아직 실행 중 조회용 딕셔너리로 변환하지 않았다. |
| `EnemyPool.pools : Dictionary<EnemyId, ObjectPool<Enemy>>` | enum ID로 `TryGetValue`하여 종류별 풀 조회 | 풀 목록 전체를 순회하지 않고 요청 ID의 풀을 찾으며, 문자열 오타를 방지한다. |
| `EnemyPool.owners : Dictionary<Enemy, ObjectPool<Enemy>>` | 반환할 객체로 `TryGetValue`하여 소속 풀 조회 | 반환 시 모든 종류의 풀이나 전체 객체 목록을 뒤질 필요 없이 원래 풀을 찾는다. |

배열과 `List<T>`는 순서를 가진 목록이며 인덱스 접근은 `O(1)`이다. 다만 ID나 객체를 기준으로 일치하는 원소를 처음부터 찾으면 최악 `O(N)`이다. `List<T>`는 실행 중 원소를 추가·삭제하는 가변 목록에 적합하고, 현재의 설정 목록에는 런타임 추가·삭제 기능이 필요하지 않아 배열을 사용했다.

딕셔너리는 순서나 몇 번째 원소인지보다 키로 값을 찾을 때 사용한다. 키 조회는 평균 `O(1)`이며 해시 충돌 등에 따른 최악은 `O(N)`이다. 키·해시 관리에 추가 메모리가 필요하므로 모든 목록을 딕셔너리로 바꾸는 대신 접근 방식에 맞춰 선택한다.

### 이렇게 나눈 설계 이유

1. **편집할 설정과 실행 중 조회를 구분한다.** 웨이브 구성과 적 프리팹 등록은 배열로 Inspector에서 설정하고, 생성된 풀과 객체의 소속은 실행 중 딕셔너리에 기록한다. 등록 목록과 런타임 관리 정보의 역할을 구분하기 위한 구조다.
2. **풀은 종류별로 재사용한다.** 같은 Basic_Enemy_left 요청은 같은 풀을 사용하고 Enemy2는 다른 풀을 사용한다. `Wave`가 직접 매번 생성·파괴하지 않고 적 ID로 요청하게 하여, 웨이브의 등장 진행과 객체 재사용 책임을 분리한다.
3. **대기 객체의 관리와 웨이브의 생존 적 관리를 분리한다.** `ObjectPool`에 객체의 재사용을 맡기고, `Wave`는 이번 웨이브의 소환 진행과 필드에 남은 적을 기준으로 완료를 판정한다.
4. **모든 생성 객체를 별도 리스트에 중복 보관하지 않는다.** 대기 객체는 `ObjectPool`이 보관하고, 소속 정보는 `owners`에 있다. 재사용과 반환을 위해 같은 객체들을 다시 별도 리스트로 관리하면 등록·제거 상태를 추가로 동기화해야 한다. 현재 범위에서는 별도 전체 객체 리스트를 두지 않는다.
5. **조회 최적화의 현재 한계를 명시한다.** 풀과 소속 풀은 딕셔너리로 조회하지만, 현재 `RequestEnemy`는 기존 풀을 조회하기 전에도 `FindPrefab`을 호출한다. 따라서 함수 전체를 평균 `O(1)`이라고 표현하지 않는다. 적 종류 수와 요청 빈도가 늘어나면 프리팹 조회 캐시 또는 기존 풀 우선 조회를 검토할 수 있으나, 이번 문서 작성으로 구현을 바꾸지는 않는다.

예를 들어 Basic_Enemy_left 객체 100개가 풀에 반환되어 대기 중일 때, 요청 시 `pools`에서 Basic_Enemy_left 풀을 한 번 조회하고 `Get()`으로 객체 하나를 꺼낸다. 사용 코드가 100개를 직접 순회해 비활성 객체를 찾는 구조가 아니다. 다만 그 요청 앞단의 프리팹 검색은 현재 등록된 적 종류 배열을 순회한다.

### 적 참조 타입과 이동 상태

- `EnemyPool`의 프리팹 등록 필드 `EnemyPrefabEntry.prefab`은 `Enemy` 타입이다. `ThrowYut` 씬에는 각 프리팹 루트의 `Basic_Enemy`, `Enemy2` 컴포넌트를 연결한다. 두 클래스가 `Enemy`를 상속하므로 같은 등록 필드와 풀 API를 사용할 수 있다.
- 풀은 `ObjectPool<Enemy>`로 적을 보관하고 `RequestEnemy`와 `ReturnEnemy`에서도 `Enemy`를 사용한다. 따라서 `Wave`는 소환 직후 컴포넌트를 다시 찾는 과정 없이 `StartMoving(waypoints)`를 호출한다. 풀의 활성화·비활성화·폐기는 적 오브젝트 전체에 적용하므로 `enemy.gameObject`를 사용한다.
- 현재 적의 행동은 이동 하나다. 상태 패턴 도입은 보류하고, 공통 부모 `Enemy`의 `IsMoving`으로 프레임마다 이동할지 결정한다. 적 종류별로 이동 속도는 프리팹에서 설정할 수 있다.

### 요청과 재사용 흐름

`Wave.SpawnEnemies`는 코루틴으로 등장 간격을 기다리고, 소환 시점마다 일반 함수인 `EnemyPool.RequestEnemy`를 호출한다. `RequestEnemy` 자체는 대기하지 않고 적 하나를 준비해 반환한다.

1. 요청받은 적 ID에 해당하는 프리팹을 찾는다. 등록되지 않은 ID이면 경고 후 `null`을 반환한다.
2. `pools`에서 해당 종류의 풀을 찾는다. 없으면 새 `ObjectPool`을 만들고 등록한다. 풀 생성 시에는 객체 생성·반환·폐기 동작을 등록하며, 적을 미리 여러 마리 만들지는 않는다.
3. `pool.Get()`으로 적 하나를 가져온다. 대기 객체가 있으면 재사용하고, 없으면 등록된 생성 함수에서 `Instantiate`한다.
4. 객체의 소속 풀을 `owners`에 기록하고, 요청받은 월드 위치·회전을 적용한다.
5. `SetActive(true)`로 활성화한 뒤 Enemy 컴포넌트를 반환한다.

예를 들어 Basic_Enemy_left 풀에 반환되어 대기 중인 객체가 100개 있다면, 한 개를 요청할 때 새로 생성하지 않고 기존 객체 하나를 꺼낸다. 대기 객체는 99개가 되고 꺼낸 객체 하나를 사용한다. 대기 객체를 모두 꺼낸 뒤 추가 요청이 오면 새 객체를 생성한다.

### 반환과 생존 적 추적의 구분

1. 사용이 끝난 객체를 `EnemyPool.ReturnEnemy(enemy)`에 전달한다.
2. `owners`에서 소속 풀을 찾아 `pool.Release(enemy)`를 호출한다.
3. 반환 콜백이 `SetActive(false)`를 실행하며, 객체는 풀 내부에서 다음 요청을 기다린다.
4. 다시 요청하면 해당 객체를 꺼내 위치·회전을 설정하고 활성화한다.

직접 `SetActive(false)`를 호출하는 것만으로는 풀에 반환되지 않는다. 현재 `ReturnEnemy`는 `activeSelf`도 검사하므로, 먼저 비활성화하면 반환이 건너뛰어진다. 현재 구조에서는 `ReturnEnemy`를 호출하고 비활성화는 반환 콜백에 맡긴다.

`owners`에는 사용 중인 객체와 반환된 객체가 모두 기록될 수 있다. `Wave`는 별도의 `HashSet<Enemy>`인 `spawnedEnemies`에 현재 필드의 적을 추적한다. 적을 소환할 때 추가하고, 처치 또는 경로 도착 시 집합에서 제거한 뒤 풀에 반환한다. 이 집합은 대상 탐색과 [완료 판정](#완료-조건)에 사용한다.

## 씬 구성과 구현 상태

- [ThrowYut 씬](../Assets/Scenes/ThrowYut.unity)의 `TurnController` 아래에 `WaveManager`, `Wave`, `EnemyPool`을 배치하고 참조를 연결했다.
- [Wave1](../Assets/Wave1.asset)를 첫 번째 웨이브로 등록했다. 현재 설정은 `EnemyId.Basic_Enemy_left` 총 100마리다.
- [Basic_Enemy 프리팹](../Assets/Prefabs/Basic_Enemy.prefab)과 [Enemy2 프리팹](../Assets/Prefabs/Enemy2.prefab)을 `EnemyPool`에 종류별 ID로 등록했다.
- 전투 시작 버튼을 누르면 첫 적이 즉시 등장하고, 이후에는 현재 테스트 설정인 0.1초 간격으로 구성 목록의 순서에 따라 소환한다.
- `Wave`의 `Waypoints` 배열에 오른쪽 아래 → 오른쪽 위 → 왼쪽 위 → 왼쪽 아래 순서로 경유점을 지정한다. 네 경유점은 모두 `Wave`의 자식이다. 첫 경유점은 소환 위치인 `Path 00 Bottom Right` `(1.65, -3.9, 0)`이며, 나머지는 `Path 01 Top Right`, `Path 02 Top Left`, `Path 03 Bottom Left`다. 경유점 좌표는 씬에서 조정할 수 있다.
- `EnemyPool`은 종류별로 풀을 만들고 요청 시 적을 활성화하여 지정한 위치에 놓는다. 반환 시 비활성화하며 이후 같은 종류의 요청에 재사용한다.
- 실행 중인 웨이브에 시작 요청이 반복되어도 중복 소환하지 않는다.
- `Wave`는 이동 시작 시 이탈 처리 콜백을 전달한다. 한 바퀴를 마친 적은 이 콜백을 통해 풀로 반환되며, 비활성화 시 `Enemy.OnDisable`이 이동 상태와 콜백을 초기화한다.

## 검증 상태

- C# 빌드를 경고 0개·오류 0개로 통과했다.
- Unity 배치 실행에서 공격에 따른 체력 감소, 공격 간격 유지, 처치 이벤트 1회 발생, 풀 반환과 재사용 시 최대 체력 복구를 확인했다.
- 웨이브 완료 검증에서는 적 두 마리를 순차 소환했다. 첫 적을 처치해 필드가 비어도 웨이브가 유지됐고, 마지막 적의 처치 또는 경로 도착 시 `WaveManager.WaveCompleted`가 한 번 전달됐다. 재시작 시 완료 상태가 초기화되는 것도 확인했다.

## 미정 및 후속 범위

- 웨이브별 적 종류·수량과 공통 등장 간격의 실제 값.
- 여러 적 종류가 한 웨이브에 포함될 때 등장 순서.
- 기지 도달 피해와 처치 재화 지급 연결.
- 웨이브 데이터가 없는 경우 및 마지막 웨이브 이후 처리.

하트 0에 따른 패배 깃발 표시는 [턴 명세](TurnSpec.md#전투-결과-깃발)에 기록한다. 일반 진화, 특별진화 및 목표지점 도착 구상은 이번 명세에서 확정하지 않는다.
