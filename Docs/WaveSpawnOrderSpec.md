# 고정 혼합 등장 순서 (2026-11-18)

작업12에서 다시 내보낸 [사용자 지정 Google Docs 탭4](https://docs.google.com/document/d/1hI6NtOWNZ2KTU-vgrUT0q4KMR9PjlM2E5JoXmvvcwuU/edit?tab=t.blkk5zag95yu)의13장 기준이다. 첫 적은 즉시,이후 게임 시간1초마다1기씩 생성하고,일반/빠른 적을 수량 비율에 맞춰 고르게 섞은 목록을 저장한다. 구체적 개체 순서는 구현 데이터이며 재도전 시 무작위로 섞지 않는다.

## 저장과 실행

기존 `WaveData.enemies : EnemyGroup[]`를 그대로 사용한다. Wave1~9의 각 항목은 `count=1`이며 배열 순서가 개체별 등장 순서다. 각 항목의 health는 작업12 표를 유지한다. Wave10은 기존 보스1기/HP6000 항목을 유지한다. 새 런타임 자료형이나 셔플 코드는 추가하지 않았다.

목록 작성 시 전체 수 T,빠른 수 F에 대해 앞 k개 항목의 빠른 수를 `floor(k*F/T)`로 정했다. 이전 항목 대비 빠른 수가 증가하는 위치에 빠른 적을 두고 나머지는 일반 적을 둔다. 따라서 어느 접두 구간에서도 이상적인 빠른 적 수와 실제 빠른 적 수의 차이가1기 미만이다. 일반 적으로 시작하는 배치는 구현 선택이며 원문이 지정한 개체 순서라고 주장하지 않는다. 이 계산은 저장할 목록 작성에만 사용했고 플레이 중 재계산하지 않는다.

`Wave.StartWave → SpawnEnemies → foreach EnemyGroup → count만큼 EnemyPool.RequestEnemy → ConfigureHealth → StartMoving`의 기존 경로가 저장 순서를 그대로 소비한다. 첫 항목 전에는 기다리지 않고 두 번째부터 WaitForSeconds를 사용한다. 씬의 공통 spawnInterval=1은 변경하지 않았다. 필드가 비었어도 목록의 남은 항목이 있으면 spawningComplete가 거짓이므로 완료하지 않는다.

## 검증 도구

[WaveOrderVerification.cs](../Assets/Editor/WaveOrderVerification.cs)는 씬에 등록된10개 데이터의 단일 개체 항목·수량·모든 접두 구간의 혼합 비율을 검사하고,실제 생성 순서를 저장 순서와 비교한다. 같은 데이터를 서로 다른 난수 시드로 두 번 실행해406기의 순서와 HP가 같음을 확인한다. 첫 실행의1웨이브는 실제1초 간격을 사용하고 나머지는 검사 중에만 간격을 단축한다. 빈 필드에서 다음 생성 대기 중 조기 완료가 없는지도 검사한다.

반복 검증에서는 TurnController를 메모리에서만 비활성화하고 씬의 Wave를 직접 실행한다. 첫10웨이브 완료 후 기존 승리 화면이 일시정지하면 두 번째 실행을 진행할 수 없기 때문이다. 따라서 이 검사는 Wave의 같은 데이터 재실행과 난수 상태 무관성을 검증하며,승리 화면의 재도전 버튼/씬 재진입 전체 흐름까지 검증한 것으로 확대하지 않는다. 해당 게임 코드는 수정하지 않았다.

배치 재실행은 별도 검증 복사본에서 `-executeMethod WaveOrderVerification.ReimportAndRun -nographics`를 사용한다. 결과는 `Logs/WaveOrderVerification.json`에 쓰고 검증 편집기를 종료한다. 실행 중 씬/에셋은 저장하지 않는다. 원본의 열린 에디터에서 직접 실행하지 않는다.

실행 결과: Unity6000.3.28f1의 ThrowYut 씬 복사본에서 **1859개 검사 통과·검사 구간 런타임 오류0**.10개 웨이브를 두 번 실행해406기의 실제 순서/HP가 저장 목록과 일치했고 난수 시드가 달라도 동일했다. [실행 결과와 두 목록](Verification/WaveOrderVerification.json). 작업12의HP 회귀907개도 통과·검사 구간 오류0이다(`Logs/WaveHealthAfterOrder.json`).

첫 실행1웨이브는 원래1초 간격을 사용했고,나머지는 검사 중에만 .01초로 단축했다. 실제 게임의 생성 간격은1초다. 검증한 코드·씬·10개 데이터와 작업본의 SHA-256을 대조했고 기존 검증 복사본/캐시를 재사용했다. 전체 빌드·화면 렌더링·난이도 플레이테스트·최종 승패 규칙은 이번 검증 범위가 아니다.
