# 기획서 대비 구현 미충족 누적 목록

> 2026-11-18 후속 구현: 상단 특별재화 HUD, 별도 잔액(시작 0), 특별소환창 열기·닫기와 준비/전투 차단을 연결했다. [특별소환 UI 명세](SpecialSummonUISpec.md)가 최신 연결 범위다. 아래 정적 점검 당시의 세부 기록 중 “창·잔액 자체가 없다”는 설명은 이 후속 구현으로 대체한다. 완주 지급·아이템 지급·30 차감·인구 검사·추첨·백호 생성은 여전히 미구현이므로 GAP-004~006은 완결 처리하지 않는다.

- 기준: [Google Docs 탭 4](https://docs.google.com/document/d/1hI6NtOWNZ2KTU-vgrUT0q4KMR9PjlM2E5JoXmvvcwuU/edit?tab=t.blkk5zag95yu), 개발 전달본 v1.3 (2026-11-17).
- 점검일: 2026-11-18. 점검 완료 범위: 01~16장 (상점과 아이템까지).
- 현재 로컬 작업본의 미커밋 변경을 포함한 코드·씬·프리팹 정적 점검 결과다. Play Mode와 실제 빌드는 이번 점검에서 실행하지 않았다.
- 중복 요구사항은 기존 ID에 장과 세부 조건을 추가한다. 현재 미해결 항목은 34개다(기능·규칙 대조 항목 33개, 개발 문서 보완 1개). ID는 재사용하거나 당겨 바꾸지 않는다. 개별 수정 작업 수나 완료율을 뜻하지 않는다.
- 기능 구현은 이번 작업 범위가 아니다. 실제 수정 후 근거를 확인해 상태를 갱신한다.
- 사용자 정정(2026-11-18): 16장 말미의 '딱 하나 구미호의 심장 또는 영혼의 결정' 및 이어지는 효과·개발자 선택 문구는 고려하지 않는다. 단일 아이템 축소 해석을 철회하고 본문의 고정 5종 진열·6종 아이템 표·사용 규칙으로 재점검한다. GAP-021과 천운부 할인·천명전 배율을 복원한다. 구미호의 01장 제외와 16장 포함은 문서 불일치로 구분하고 특정 5종을 새로 확정하지 않는다. GAP-013 제외는 유지한다.
- 10장에는 피해·공격 판정의 개발 완료 전달과 추가 설계 질문·신규 구현 요청 중단이 명시되어 있다. 이번 사용자의 10장 점검 요청에 따라 차이만 기록하며, 이 기록을 변경 승인이나 신규 구현 지시로 간주하지 않는다. 미확정 판정·속도 수치를 새로 정하지 않는다.

### GAP-001 — 10웨이브와 웨이브별 적 HP·최종 보스 데이터

- 요구: 1~9웨이브 진행 후 10웨이브에 HP 6000의 보스 1기만 등장한다.
- 현재: `Assets/Scenes/ThrowYut.unity`의 WaveManager에는 Wave1, Wave2만 등록되어 있다. `Assets/Wave1.asset`은 일반·빠른 적·보스 각 1기, `Assets/Wave2.asset`은 일반 적 3기다. `Assets/Prefabs/BossEnemy.prefab`의 maxHealth는 10이며 현재 스폰 경로에는 웨이브별 HP를 덮어쓰는 처리가 없다.
- 미충족: 3~10웨이브 데이터와 전체 편성, 보스의 최종 웨이브 배치와 HP 6000 적용.
- 13장 연결: 10웨이브 전투 시작 즉시 보스 1기만 생성하며 추가 일반·빠른 적·중간 보스는 없다. 첫 적 즉시 생성 구조는 있지만 해당 편성 데이터는 없다. 일반 웨이브의 고른 고정 혼합 순서는 GAP-033에서 추적한다.
- 12장 구조 누락: WaveData.EnemyGroup에는 enemyId와 count만 있고 개체 HP 값은 없다. Enemy.OnEnable은 프리팹 maxHealth로 복구하고 EnemyPool.RequestEnemy 및 Wave.SpawnEnemies에는 웨이브별 HP 적용 경로가 없다. 일반·빠른 적·보스 프리팹 maxHealth는 모두 10이다. 같은 종류도 웨이브마다 달라지는 HP를 데이터와 스폰/풀 재사용에 일관되게 적용해야 한다.

### GAP-002 — 보스 처치 즉시 최종 승리

- 요구: 10웨이브 보스 처치 즉시 승리한다.
- 현재: `Assets/Scripts/Turn/TurnController.cs`의 EndBattle은 등록된 마지막 웨이브 완료 시 승리한다. 현재는 2웨이브 완료가 승리 조건이다. `Assets/Scripts/Wave/Wave.cs`는 죽음 애니메이션까지 끝나 dyingEnemies가 비어야 완료된다.
- 미충족: 최종 보스 처치 이벤트에 따른 즉시 최종 승리 판정. 사망 연출 종료를 기다리는 일반 웨이브 완료와 구분해야 한다.
- 13장 연결: 최종 보스 처치 즉시 승리를 재확인한다. 현재 등록된 마지막 웨이브 완료에 의존하는 구조와 다르다.
- 14장 연결: 보스 처치 보상 100(천명전 적용 시 200)을 지급한 뒤 승리로 전환한다. 즉시 승리는 보상 정산을 생략한다는 뜻이 아니며 GAP-035와 지급 순서를 맞춰야 한다.
- 16장 재점검: 천명전 적용 시 보스 보상 200을 지급한 뒤 승리한다. 최종 승리 화면에는 보스 처치 보상·획득 엽전을 표시하지 않는 조건이 있다. 실제 정산과 화면 표시는 별개이며 결과 UI 장과 연결해 점검한다.

### GAP-003 — 보스 탈출 즉시 패배

- 요구: 하트가 남아 있어도 보스 탈출 시 즉시 패배한다.
- 현재: Wave의 EnemyArrived는 적 정보를 전달하지 않는다. TurnController.LoseLife는 모든 탈출에 하트 1만 감소시킨다. BossEnemy에는 별도 동작이 없다.
- 미충족: 보스 탈출 구분과 즉시 패배 연결.
- 13장 연결: 보스 탈출 즉시 패배를 재확인한다. 패배 이후 실제 전투 중단은 GAP-034와 함께 연결해야 한다.
- 12장 연결: 일반·빠른 적은 탈출 시 하트 -1, 보스는 속도·잔여 하트와 관계없이 즉시 패배다. 현재 일반·빠른 적 처리는 일치하지만 보스도 같은 -1 처리다.

### GAP-004 — 백호 대장군·맹호참과 특별소환

- 요구: 준비 중 특별재화로 백호 대장군을 소환해 전투에 사용한다.
- 현재: 백호 대기·공격 이미지 등은 있으나 전투용 클래스·프리팹과 특별소환 처리, 재화 소비·배치 연결은 확인되지 않는다.
- 미충족: 백호 전투 유닛과 준비 단계 특별소환 기능.
- 03장 연결: 특별소환은 준비에서만 허용하고 전투·일시정지에서는 차단해야 한다. 현재 기능 자체가 없어 상태별 허용·차단도 미충족이다.
- 04장 연결: 백호도 일반 유닛과 같은 시작 칸에 생성해야 한다. 일반 유닛은 현재 Cell 01에 생성되며, 특별소환의 공통 시작 칸 연결은 미구현이다.
- 05장 연결: 백호는 인구 3, 업기·진화 불가이며 항상 1기씩 선택·이동한다. 백호 유닛 자체가 없어 해당 동작도 미구현이다. 공통 점유·자리 표현은 GAP-018, 일반 유닛 묶음은 GAP-019에서 추적한다. CharacterInfoPanel도 현재 일반 5종만 처리해 백호 정보 연결이 필요하다.
- 11장 획득 조건: 특별재화 30을 소비해 등록 후보에서 무작위 소환한다. 현재 후보는 백호 한 종류라 실제 결과는 백호다. 후보 등록·소환·비용 결제 연결이 없으며, 임의의 희귀도나 추가 후보 추첨 규칙을 만들지 않는다.
- 11장 능력치: ATK 100, AS 0.5회/초(간격 2초), 단일 대상 기준 기본 DPS 50, 본인 중심 사거리 3.5, 표적 방향 기준 총 120도다. 이를 설정할 백호 전투 프리팹·전용 동작이 없다. 수치는 초기값·플레이테스트 조정 대상이며 사용자 제공 기준으로만 기록한다.
- 11장 맹호참: 매 기본 공격이 맹호참이다. 타격 순간 본인 중심의 반경 3.5·총 120도 부채꼴 안 모든 적에게 각각 공격력 100%를 한 번 적용한다. 별도 스킬 버튼·스킬 재사용 대기시간은 요구하지 않는다. 현재 부채꼴 판정·다중 대상 피해 연결은 없으며 일반 Ally.ApplyAttack은 표적 한 기에만 피해를 준다.
- 11장 표적 규칙: 일반 유닛과 같은 최근접 최초 선택·유효 표적 유지가 필요하다. 공통 기반은 Wave/Ally에 있지만 백호가 없어 실제 적용은 미연결이다.

- 03장 전환 누락: StartBattle은 윷 조작 버튼을 갱신하지만 아군 범위·행동 버튼·정보창·상점·인벤토리를 일괄 닫지 않는다. BattleStarted의 코드 구독은 BattleStateHUD의 시작 표시뿐이며 기존 준비 UI를 정리하지 않는다.
- 일시정지 메뉴의 계속하기·메인으로·게임 종료와 상태별 입력 차단이 없다. GameSpeedButton은 클릭 시 Time.timeScale을 직접 양수로 설정하므로, 일시정지 중 배속을 제공한다면 정지 상태를 유지하도록 연결해야 한다. 이는 현재 일시정지 구현 결함을 실행 재현한 것이 아니라 구현 시 필요한 연결 조건이다.
- 08장 진화 시점: 준비 단계이고 윷 결과 처리가 끝났으며 유닛이 이동 중이 아닐 때만 허용한다. CanEvolve는 단계·CurrentYutResult·IsThrowing을 검사하지 않으며 버튼과 실제 RequestEvolution도 같은 조건을 따른다. 미사용 결과가 남아 있거나 윷 연출 중에도 재료만 맞으면 진화가 가능한 코드 경로가 있다. 전투 차단 누락과 함께 이 항목에서 추적한다. 현재 이동은 동기 처리여서 별도 '이동 중' 실행 구간의 결함을 단정하지 않으며 비동기 연출 도입 시 검사 연결이 필요하다.

### GAP-009 — 메인 이동·종료와 초기화 확인

- 요구: 중간 저장 없이 메인 이동·종료 시 진행이 사라지고, 나가기 전에 초기화를 확인한다.
- 현재: 게임 중 메인 복귀·종료 메뉴와 확인 창이 없다. TitleScreenController.QuitGame은 즉시 종료한다. 중간 저장·이어하기 코드는 확인되지 않는다.
- 미충족: 게임 중 나가기 경로, 확인·취소 흐름, 진행 초기화와 화면 이동 연결. 저장 기능의 부재 자체는 요구에 맞는다.
- 03장 상세 조건: 전투 중 메인·종료는 일시정지 메뉴를 거친다. 나가기 확인에서 취소하면 기존 일시정지 메뉴로 돌아가 진행을 유지하고, 확인하면 진행을 초기화해 메인으로 이동하거나 종료한다. 해당 메뉴·확인 흐름 모두 미구현이다.

### GAP-010 — 웨이브 기본 완료 보상

- 16장 연결: 천명전 적용한 바로 다음 전투의 기본 완료 보상은 60→120이다. 적을 놓쳐도 하트가 남아 완료하면 적용한다. 중복 사용·효과 대상 전투 관리는 GAP-007에서 추적한다.

- 요구: 1~9웨이브 완료 시 기본 완료 보상을 지급한 뒤 다음 웨이브 준비로 이동한다.
- 현재: TurnController.EndBattle → EndTurn은 웨이브 번호 증가와 준비 전환만 한다. 보상 지급 코드가 없다.
- 미충족: 완료 보상 지급과 중복 지급 방지. 보상 액수는 02장에 없으므로 해당 수치가 정의된 장 점검 시 연결한다.
- 13장 연결: 하트가 남으면 일부 적이 탈출해도 기본 완료 보상을 지급한다. 전원 처치 조건은 없다. 하트 0이면 정산하지 않고 동일 전투에서 한 번만 지급해야 한다. 현재 EndBattle의 하트 0 차단은 있으나 보상 자체가 없다.
- 14장 수치: 1~9웨이브 완료마다 일반재화 60(기본 던지기 3회분), 9회 합계 540이다. 10웨이브에도 60을 더 준다고 가정하지 않으며 보스 보상은 GAP-035로 관리한다.

### GAP-011 — 패배 후 전체 초기화 재도전

- 요구: 패배 후 재도전하면 모든 진행을 초기화해 1웨이브부터 시작한다.
- 현재: BattleStateHUD.ShowDefeat은 패배 패널만 표시한다. 재도전 버튼 연결과 재시작·전체 초기화 경로는 확인되지 않는다.
- 미충족: 패배 후 재도전 입력과 초기화. 웨이브·하트·편성·재화·아이템·효과·구매 이력 등을 새 게임 상태로 돌려야 한다.

### GAP-012 — 빌드의 메인 화면 시작 흐름

- 요구: 메인에서 게임시작을 선택해 새 게임의 1웨이브 준비로 진입한다.
- 현재: Title 씬과 TitleScreenController.StartGame의 ThrowYut 로드는 있다. 그러나 `ProjectSettings/EditorBuildSettings.asset`의 활성 씬에는 ThrowYut만 있고 Title이 없다.
- 미충족: 현재 기본 빌드 설정에서 타이틀을 시작 씬으로 포함하고 게임 씬으로 연결. 별도 빌드 프로필의 덮어쓰기 여부는 이번 점검에서 확인되지 않았으며 실제 빌드 실행은 하지 않았다.

### GAP-014 — 행동 후보가 없는 윷 결과 자동 소모와 사유 안내

- 요구: 소환·이동 등 행동 가능한 후보가 전혀 없는 결과는 자동 소모해 전투 시작을 계속 막지 않는다.
- 현재: TurnController.ReceiveYutResult는 이동 불가능한 빽도만 자동 소모한다. 그 외 결과는 이동 가능 여부와 소환 칸 여유를 함께 검사하지 않는다. ChooseSummon에서 소환 실패 시 결과는 유지된다.
- 영향: 소환 칸이 가득 차고 해당 결과로 이동할 아군도 없으면 사용할 수 없는 결과가 남고, StartBattle은 CurrentYutResult.HasValue 때문에 계속 차단된다. 이는 코드에서 확인한 경로이며 Play Mode로 재현하지 않았다.
- 미충족: 빽도를 포함한 모든 결과에 대해 실제 소환·이동 후보가 없는지 판단해 자동 소모. 불가능한 소환 버튼의 상태 표시도 함께 점검한다.
- 06장 상세 조건: 자동 소모 시 짧은 사유 안내 후 준비 조작으로 복귀한다. 현재 이동 불가능한 빽도는 즉시 결과를 비우지만 사유 안내가 없다. 일반 결과의 소환 버튼은 시작 칸 여유를 검사하지 않아 가득 찬 상태에서도 활성화된다. 가능한 행동 표시와 실제 소환 가능 여부를 일치시켜야 한다.
- 재화가 충분하면 다시 유료로 던질 수 있고 부족해도 전투 시작 등 나머지 가능한 조작은 유지해야 한다. 무환불·재결제는 GAP-006, 전투 시작 시 미사용 결과 안내는 GAP-015와 구분한다.

### GAP-015 — 미사용 윷 결과에 따른 전투 시작 차단 안내

- 요구: 미사용 윷 결과가 있으면 먼저 처리하라는 안내를 표시한다.
- 현재: TurnController.StartBattle은 CurrentYutResult.HasValue 또는 IsThrowing일 때 단순 return한다. 미사용 결과에 대한 안내 이벤트·메시지 표시는 확인되지 않는다.
- 미충족: 전투 시작이 미사용 결과로 막힌 이유와 먼저 처리할 행동을 사용자에게 알리는 안내.

### GAP-016 — 이동 이력에 제한되지 않는 빽도와 후퇴 경로 선택

- 요구: 빽도는 지나온 길로 제한하지 않는다. 허용된 후퇴 연결이 여러 개면 플레이어가 선택한다. 시작 칸에서 빽도는 마지막 칸으로 이동하며 퇴장·보상을 발생시키지 않는다.
- 현재: YutActionController.GetPreviousCell은 travelHistory의 직전 칸 하나만 반환한다. CanMove와 SelectAlly도 이 칸 하나만 후보로 사용한다. 같은 칸·종류·성급의 그룹도 빽도에서는 직전 칸이 같은 유닛만 묶는다.
- 영향: 같은 칸에서도 이동 이력에 따라 빽도 후보가 달라지며 후퇴 분기 선택을 할 수 없다. 새 일반 유닛은 Cell 01에 생성되고 이력을 [0, 1]로 넣어 첫 빽도는 Cell 00으로 이동하지만, 이후 이력이 [0]만 남으면 추가 빽도 후보가 사라진다. 직전 칸으로 갔다가 다시 빽도로 전진 방향을 고르게 되는 등 이동 이력 되돌리기와 구조상 후퇴는 다른 동작이다.
- 미충족: 명시적인 허용 후퇴 연결, 복수 후보 표시·선택, 시작→마지막 칸 규칙과 무보상 처리. 후퇴 연결은 전진 연결을 무조건 뒤집거나 임의 이웃을 허용하지 않고 04장의 맵 자료와 대조해야 한다.
- 주의: 새 유닛의 Cell 01→00 동작만으로 시작 칸 빽도가 완전히 미구현이라고 단정하지 않는다. 시작·마지막 번호 대응과 이력에 무관한 일관성 확인이 필요하다.
- 05장 연결: 현재 빽도 그룹은 같은 종류·성급이어도 직전 칸이 다르면 나뉜다. 05장의 자동 묶음 조건에 없는 이동 이력이 그룹 구성에 개입한다. 후퇴 경로 판정과 묶음 선택을 함께 정합화해야 한다.

### GAP-017 — 실제 맵과 대응하는 전진·후퇴 노드 도식

- 구분: 게임 기능 결함과 별개의 개발 문서 보완 항목.
- 요구: 실제 맵에 시작·마지막 칸, 노드 번호·좌표, 전진·허용 후퇴 연결, 지름길 분기·중앙 허용 방향을 대응시킨 노드 도식이 필요하다. 세부 좌표를 사용자에게 다시 결정받는 항목은 아니다.
- 현재: YutBoard.cs에 29칸 ASCII 배치와 전진 연결이 있고 ThrowYut 씬에 Cell 00~28 좌표가 있다. Docs/YutBoardSpec.md에는 좌표 환산식·분기 설명이 있지만 전체 좌표 대응표, 허용 후퇴 연결과 최신 시작·마지막·퇴장 경계를 함께 표시한 도식은 확인되지 않는다.
- 문서 불일치: YutBoard.StartCellId와 코드 그림·로컬 명세는 Cell 00을 시작으로 부르지만 실제 일반 소환은 Cell 01이다. 04장은 전통 윷놀이에서 첫 도로 이동하는 칸을 시작 칸으로 정한다. 로컬 명세에는 완주가 아직 '미정 규칙'으로 남아 있다.
- 미충족: 기존 맵·코드·씬을 대조한 최신 노드 도식과 번호·좌표·허용 방향 대응, 시작 칸 용어 정리, 이미 확정된 완주·빽도 규칙의 개발 문서 반영. Cell 01 일반 소환 자체는 04장의 시작 칸 설명과 부합할 수 있어 별도 소환 위치 오류로 세지 않는다.

### GAP-018 — 인구 가중치에 따른 칸 수용량과 백호 자리 표현

- 요구: 일반 1·2성은 인구 1, 백호는 인구 3. 모든 칸의 총인구 상한은 6이며 혼합 배치가 가능하다. 백호만 있으면 최대 2기다. 백호의 자리 표현은 인구 3임을 읽을 수 있어야 한다.
- 현재: YutBoardOccupancy.HasSpace는 alliesByCell[cellId].Count와 incomingCount를 더해 6과 비교한다. 소환·이동 모두 개체 수 기준이며 Ally에는 인구 값이 없다. ArrangeAllies는 모든 유닛을 같은 크기의 1자리로 취급한다.
- 미충족: 유닛별 인구 비용과 합계 계산, 소환·이동 후보·최종 이동에 가중 인구 적용, 백호의 인구 3을 읽을 수 있는 배치 표현. 백호가 아직 없으므로 실제 과밀 배치가 현재 발생했다고 주장하지 않는다.
- 예시: 일반 4기와 백호 1기는 인구 7이라 불가해야 하고, 일반 3기와 백호 1기는 인구 6으로 가능해야 한다. 백호 2기는 가능하지만 세 번째는 불가해야 한다.
- 07장 연결: 목적지 현재 인구+이동 묶음 전체 인구가 6 이하인 후보만 허용한다. 현재도 후보 표시와 이동 확정 시 개체 수를 재검사하지만 인구 가중치가 없어 특별유닛의 3인구 조건을 적용하지 못한다. 도착 후 현재 인구를 갱신해 표시하는 UI도 확인되지 않는다. 확정 전 예상 인구 표시는 GAP-023에서 관리한다.
- 11장 연결: 백호 인구 3과 일반 아군의 혼합 배치는 총인구 6 이내에서만 허용한다. 현재 개체 수 검사만으로는 이 조건을 표현하지 못한다.
- 15장 특별소환 경계: 시작 칸 현재 인구가 0~3이면 백호 인구 3 추가가 가능하고 4~6이면 불가다(재화 조건 별도). 만석 6일 때만 차단하는 것은 부족하다. 현재 특별소환 검사가 없으며 일반 소환의 HasSpace 기본 인구 1 검사로 대체할 수 없다.

### GAP-019 — 최대 3기 자동 업기 묶음과 선택 단위

- 요구: 같은 칸·종류·성급의 일반 유닛은 최대 3기씩 자동 묶인다. 수량 4/5/6은 각각 3+1/3+2/3+3이며 클릭한 유닛이 속한 묶음만 이동한다. 구성 변화 시 별도 묶기 버튼 없이 갱신한다.
- 현재: YutActionController.GetMovingAllies는 같은 종류·성급의 모든 아군을 반환하며 3기 제한이나 소속 묶음 구분이 없다. 전진 이동에서는 4~6기도 전부 한 그룹이다. 빽도에서 이동 이력으로 나뉘는 문제는 GAP-016에도 연결한다.
- 영향: 같은 종류·성급 4기와 목적지 빈자리 3인 경우, 문서상 3기 묶음은 이동할 수 있지만 현재는 4기를 한 번에 넣으려 하여 후보를 제외한다. 이는 코드로 확인한 경로이며 Play Mode 재현은 하지 않았다.
- 미충족: 3기 단위 분할, 개별 유닛의 소속 묶음 결정, 해당 묶음만 선택·이동, 소환·이동·진화·퇴장 후 구성 갱신. 두 줄의 시각 배치와 이동 묶음은 별개로 유지한다.
- 묶음 내 구체적인 순서·식별 정책은 구현 선택이며 05장에 없는 고정 정책을 사용자 결정으로 간주하지 않는다.
- 07장 연결: 인구를 맞추기 위해 이미 구성된 묶음 일부만 이동하는 것은 금지한다. 현재 전체 그룹의 원자적 이동은 있으나 그룹 경계가 최대 3기 규칙과 다르다. 도착 후 구성 변화에 따른 3기 단위 자동 묶음 갱신도 필요하다. 3기 묶음+목적지 일반 4기의 부분 이동 금지는 현재 개수 검사로 충족한다.

### GAP-027 — 소 철퇴병의 직격과 주변 피해

### GAP-028 — 전투마다 첫 공격 준비 상태 초기화 보장

### GAP-029 — 도사·궁수 투사체의 동일한 일정 속도 이동

- 요구: 마법탄·화살은 같은 일정 속도로 현재 표적을 추적하며, 거리와 표적 이동에 따라 비행 시간이 달라진다. 도착 시각에 맞추는 가감속은 없다. 구체적인 속도는 기존 구현 설정을 참조한다.

### GAP-030 — 발사 후 공격자 기준 사거리 이탈 시 투사체 소멸

- 요구: 비행 중 표적이 공격자 중심의 사거리 밖으로 나가면 즉시 소멸·무피해이며 이미 발사된 투사체에도 적용한다. 명중 시에도 유효성을 검사하고 다른 적으로 바꾸지 않는다.
- 현재: HomingProjectile은 표적의 존재·활성·체력·풀 활성 버전만 검사한다. Launch는 공격자나 사거리를 받지 않아 공격자 중심 거리 검사가 없다.
- 차이: 발사 후 원래 공격자의 사거리 밖으로 나간 표적도 살아 있고 같은 활성 버전이면 계속 추적해 피해를 줄 수 있다. 사망·탈출·재사용 시 소멸, 다른 적으로 재표적하지 않음, 피해 한 번 적용은 이미 구현되어 있다.

### GAP-031 — 전사·창병의 공격 시작 표적 유지와 근접 타격 판정

- 요구: 전사·창병은 공격 시작 때 사거리 안에 있던 표적을 타격까지 유지한다. 이후 거리 이탈만으로 취소하지 않는다. 사망·탈출이면 피해 없이 동작을 마치고 다른 적에게 진행 중 공격의 피해를 옮기지 않는다. 기존 대기시간은 유지한다.
- 현재: Ally.LateUpdate와 TryBeginAttackEvent는 RefreshTarget을 호출하며, 기존 표적이 사거리 밖이거나 사망·탈출하면 다른 유효 표적을 찾는다. 표적이 없으면 OnTargetUnavailable이 공격 상태를 끄고 대기 애니메이션으로 전환한다. ApplyAttack은 그 시점 CurrentTarget에 피해를 준다. 별도의 공격 시작 표적을 보관하지 않는다.
- 차이: 진행 중 공격이 새 표적으로 옮겨질 수 있고, 대상 부재 시 동작을 취소하며, 생존한 원래 표적의 단순 거리 이탈에도 예정 타격을 보장하지 못한다. nextAttackTime 자체는 재표적 때 초기화하지 않아 대기시간 보존은 충족한다.

### GAP-032 — 적 종류별 속도 비율과 경로 통과 시간

- 2026-11-18: 사용자가 GAP-013은 구현 대신 기획 문서를 수정해야 한다고 결정했다. 미충족 목록·개수에서 제외하고 ID는 보존한다. 현재 1→2→4→1배 동작을 1↔2배로 바꾸는 구현 작업은 요구하지 않는다. Google Docs 원문은 이번 작업에서 수정하지 않았다.

### GAP-034 — 하트 0 패배 시 스폰·공격 종료와 종료 판정 정합성

- 종료 타이밍 관찰: 13장은 생성 예정 0·생존 적 0을 조건으로 쓰지만 현재는 dyingEnemies가 비고 사망 연출 반환이 끝나야 완료한다. Docs/EnemySpec.md에도 이 대기를 명시하고 있어 기존 의도와 기획 기록의 차이로 남긴다. 일반 웨이브의 사망 연출 대기를 금지하는 명시 문구는 없어 신규 결함 수에 넣지 않는다. 보스 즉시 승리는 GAP-002와 구분한다.
- 플레이테스트의 누수 수·잔여 하트·일반재화·2성 수·특별재화·백호 수는 검증 체크리스트다. 자동 로거·파일 저장이 명시된 것은 아니므로 전용 로거 부재를 신규 결함으로 세지 않는다. 실제 해당 기록·검증 완료 증거는 이번에 확인하지 않았다. HP 합계로 클리어율이나 난이도 검증 완료를 주장하지 않는다.
- 앞서 내보낸 13장 본문과 현재 코드·씬·로컬 명세의 정적 비교다. Play Mode의 생성 순서·패배 후 중단·종료 타이밍을 재현하지 않았고 밸런스 플레이테스트도 하지 않았다.

## 14장 확인 결과: 충족 사항과 점검 범위

- Coin HUD는 숫자 표시 컴포넌트와 초기값 120이 있다. 시작 표시와 실제 경제 상태 관리의 완료 여부를 구분한다.
- 처치 이벤트·처치 수 집계는 있지만 재화 지급 연결은 없다. 완료 보상과 처치 보상은 별개의 사건이다.
- 웨이브별 전원 처치 수입은 84/92/100/104/108/108/112/116/120으로 합계 944다. 실제 적 편성이 다르고 경제도 없어 현재 게임에서 이 수입이 나온다고 주장하지 않는다.
- 무환불·같은 판 전액 이월·다음 판 미이월은 기존 경제·초기화 항목을 구체화했다. 각 정책마다 별도 ID를 추가하지 않았다.
- 앞서 내보낸 14장 본문과 현재 관련 코드 검색·처치/종료 코드·씬 표시 초기값을 정적으로 대조했다. Play Mode 수입·차감·할인·보스 보상을 검증하지 않았다.

## 15장 확인 결과: 중복 및 점검 범위

- 일반 퇴장 보상은 2성이 1성 3기 합계와 같고 백호 퇴장은 비용 30보다 적은 15다. 현재 경제를 구현·시뮬레이션한 결과가 아니라 문서의 수치 관계를 대조한 것이다.
- 기존 GAP-004/005/006/018/023/024가 같은 기능 누락을 이미 관리하므로 새 ID를 만들지 않고 구체적 수치·경계·순서를 추가했다.
- 07장의 취소선 예시를 임의로 복원한 것이 아니라 15장에 명시된 도착 안내의 보상 합계 표시 요구를 기록했다. 두 장의 표현 차이는 원문 그대로 보존한다.
- 현재 코드 검색에서 특별재화 상태·특별소환 전용 클래스·백호 프리팹 연결은 확인되지 않는다. 일반 DeployAlly는 윷 결과로 일반 5종을 고르는 흐름이며 특별소환 구현으로 간주하지 않는다.
- 앞서 내보낸 15장 본문과 현재 코드·씬 연결의 정적 점검이다. 특별소환 성공/실패·재화 보존·인구 경계·퇴장 보상은 Play Mode에서 실행 검증하지 않았다.

## 16장 확인 결과: 사용자 정정 반영 재점검

- '딱 하나 구미호의 심장 또는 영혼의 결정'과 이어지는 사용 효과·개발자 선택 문구를 고려하지 않는다. 단일 품목 축소와 GAP-021 제외 판단을 철회했다.
- 고정 5종 진열, 상품별 1회 구매·재입고 없음, 구매 이력·인벤토리 유지, 사용형 준비 단계 사용, 6종 표의 개별 효과와 가격을 점검한다. 무작위 진열은 향후 확장이다.
- 실제 UI의 6종 진열, 가격 100 일괄 표시, 임시 설명과 빈 구매 이벤트를 GAP-007에 기록했다. 구매·사용·대기 효과·조건별 정산·재화/하트 반영 코드는 없다.
- 구미호는 01장 제외와 16장 표 포함이 상충한다. 이 불일치는 남기되 다른 다섯 아이템의 확정 효과를 누락하거나 특정 5종을 사용자 확정으로 간주하지 않는다. 하트 리셋의 세부 값을 임의로 정하지 않는다.
- 복 주머니의 기대값 200과 천운부의 비용 4 절약/25회 회수는 기획 수치 계산이며 실전 경제 검증 결과가 아니다.
- 원문은 앞서 내보낸 16장 본문, 구현 증거는 현재 상점·재화·하트 코드/씬의 정적 점검이다. 코드·씬·Google Docs는 바꾸지 않았고 Play Mode 구매·사용·효과 검증은 하지 않았다.
